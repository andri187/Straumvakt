## Risks I noticed

1. **Orphan row `b6771541`** ("VCP Lab — N1 driver access (sandbox)") — this pre-existing `installation`-type agreement is counterparty=N1 ehf but the new VCP Lab agreement (`7dc9f9d4`) is counterparty=Straumvakt. The two rows cover the same installation (`0909cff6`) with different orgs. After `--apply` there will be two active `installation` agreements on VCP Lab. If billing resolution picks the first one found (no deterministic ordering), it could pick the old N1-counterparty row instead of the new Straumvakt one. The script does NOT delete it — operator should decide whether to manually set `status='superseded'` on `b6771541` after apply.

2. **`effective_from` sourced from org `created_at`** — the rate references' `effective_from` timestamps (`2026-05-04T23:20:35`) come from the legacy `tariff_definitions` row's creation timestamp, not from a contractual start date. Acceptable for a pilot seed but worth noting if historical cost re-computation is ever needed.

3. **VCP Lab DSO = Veitur AD1 but different supplier UUID** — the pre-flight shows Straumvakt's Veitur record is `86f8a39f` while N1's is `7c38fab3`. The script uses `7c38fab3` as the source for `VEITUR-AD1`'s `effective_from`. Both share the same price (8.64 kr/kWh), so the rate itself is correct. No billing error, but the `notes` column on the rate reference will only reference N1's TD UUID.

4. **No cross-tenant pollution** — all clause `agreement_id` foreign keys route through the correctly-scoped `installation` → `counterparty_org_id` chain. DSO clauses are org-neutral (`supplier_org_id=NULL`); ELE clauses are scoped to N1 ehf. No data crosses tenant boundaries.

5. **BearerRules = 0** — pilot deliberately defers USRF/INT bearer rules to post-pilot per ADR 0019. Correct as documented; not a bug.

## Recommended next step

**Looks mostly clean — but resolve the orphan before applying.**

Specifically:
- Before running `--apply`, manually set `status = 'superseded'` (or `'cancelled'`) on agreement `b6771541` ("VCP Lab — N1 driver access (sandbox)") so there is only one active `installation` agreement on VCP Lab after the migration lands.
- Alternatively, confirm that billing resolution has deterministic tie-breaking that would always prefer the Straumvakt-org row — if so, the orphan is harmless and can be cleaned up separately.

Once that is resolved: operator can run `--apply` and the SQL looks correct.
