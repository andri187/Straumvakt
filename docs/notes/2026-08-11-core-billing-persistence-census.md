# Core billing persistence census — 2026-08-11

**Purpose.** Stop the assumption loop. Every prior Core-billing doc in this repo cites
earlier Core-billing docs; several of those citations are now stale, and at least four
source-file headers describe capabilities that were never built. This census was taken by
five readers working in parallel over disjoint areas, each instructed to read source and
ignore prior documentation. 310 rows, every one carrying a file:line.

Method: five parallel read-only passes over `schema-and-migrations`,
`repositories-and-idempotency`, `routes-and-permissions`, `calculation-delivery-export`,
`tests-and-audit`. Worktree `E:\Claude\Straumvakt-core-billing`, branch
`scratch/claude-a-core-billing-2026-08-10`, tip `47a99f6`.

## The ten required findings

Each is marked **verified true**, **verified false**, **narrowed**, or **unknown**.

### 1. Settlement snapshots have no durable table — VERIFIED TRUE

No settlement- or snapshot-shaped model exists in any of the nine `prisma/schema/*.prisma`
files, and `packages/shared/src/db/commercial.ts` declares 18 tables (:55-459), none of
them settlement-shaped. The only durable per-session money record is
`reports.session_ledger` ([commercial.prisma:297-336](prisma/schema/commercial.prisma#L297)):
one nullable `cost_isk_minor` (:308) and **one** `tariff_definition_id` (:309) pointing at
`billing.tariff_definitions`, whose `compute_rule` JSONB is mutated in place (:129).

No rate version, no unit price, no effective window, no ex-VAT/VAT split is stored. The
accusation `settlement.ts` makes about the current path is verified at source:
[projections.ts:438-444](apps/api/src/lib/ocpp/projections.ts#L438) writes only
`resolved.dsoTariffDefinitionId` and carries a TODO saying the retailer component would
need "a JSONB breakdown or sibling FK column" the schema does not have.

### 2. Statement material has no durable table — VERIFIED TRUE

`billing.statements` was **dropped** at
[prisma/migrations/20260807120000_drop_never_used_tables/migration.sql:47](prisma/migrations/20260807120000_drop_never_used_tables/migration.sql#L47),
together with `billing.invoice_lines` (:45), `billing.invoices` (:46),
`billing.subscriptions` (:49), `billing.contract_period_accumulators` (:52) and
`reports.billing_period_summary` (:88).

Nothing replaced them. `apps/api/drizzle/0000_baseline.sql` — the post-drop Drizzle
baseline — creates ten billing/reports tables and not one is statement- or invoice-shaped
(`bill_object_members` :528, `bill_objects` :536, `billing_lines` :550, `cost_factors`
:566, `contracts` :579, `cost_centers` :594, `driver_contracts` :622, `session_ledger`
:672, `tariff_definitions` :690, `tariffs` :705).

The dead Postgres enum outlived its table on both sides
([commercial.prisma:72](prisma/schema/commercial.prisma#L72),
[packages/shared/src/db/commercial.ts:35](packages/shared/src/db/commercial.ts#L35)).

### 3. No reliable persisted source for driver-month / connector-month — VERIFIED TRUE

The failure is different on each side, and neither is a missing query — both are missing
history.

**Connector.** `assets.connectors` carries a mutable current-state
`status String @default("unknown")` plus `statusUpdatedAt`
([assets.prisma:437-438](prisma/schema/assets.prisma#L437)) — no `activeFrom`,
`activeUntil`, or `decommissionedAt`, and no history table.
`assets.charging_stations` has `installDate` (:260) and `warrantyExpires` (:261) but **no
status, active, or removed column anywhere** in its 150 lines (:248-398), so a charger's
removal leaves no timestamp at all. "Connector enabled during month M" is observable now
and not reconstructible afterwards.

**Driver.** `subscription.ts:10` defines an active driver as one "with charging or
reporting activity in the month". Charging activity is derivable from `charging.sessions`
(`userId` :20, `startedAt` :22) — but `session.userId` is nullable, and *reporting
activity* has no persisted event of any kind. The roster side is worse:
`agreements.driver_group_memberships` has `addedAt` **only**
([commercial.prisma:570](prisma/schema/commercial.prisma#L570)) with no `removedAt`, and
`@@unique([driverGroupId, userId])` (:575) forbids the second row that history would
require. Removal is a hard delete leaving nothing behind.

`tenancy.memberships` does carry `invitedAt`/`acceptedAt`/`suspendedAt`/`revokedAt`
([identity.prisma:624-628](prisma/schema/identity.prisma#L624)) — but a driver is not a
Membership: drivers carry `User.audience = 'driver'`
([identity.prisma:660](prisma/schema/identity.prisma#L660)). The one history-preserving
membership shape in the whole schema is `billing.bill_object_members`
(`effectiveFrom`/`effectiveTo`, commercial.prisma:628-629), and it models bill attribution,
not driver activity.

### 4. Plug-time billing lacks its inputs — VERIFIED TRUE, and narrowed in a useful direction

A `charging.sessions` row has exactly seven timestamps and not one is a plug, unplug, or
charging-ceased instant: `started_at` (charging.prisma:22), `ended_at` (:23), `created_at`
(:27), `updated_at` (:28), `completed_session_seen_at` (:53, an AMQP-ingest *observation*
time), `ocpp_stopped_at` (:106) and `cdr_stopped_at` (:107). The last three are per-source
mirrors of the same event — "the transaction stopped" — so they cannot distinguish
charging-ceased from cable-removed, which is exactly the pair
[plug-time.ts:69-76](packages/commercial/src/core-billing/plug-time.ts#L69) needs. A
case-insensitive grep of the whole schema tree for `plug|unplug|occupanc|cable|cease|idle`
finds only `cable_type` (a Mode 3 / Type 2 string), one substring match, and prose.

**The narrowing that matters:** the inputs exist and are deliberately destroyed.
`charging.live_sessions` holds `connected_at`, `charging_started_at`, `last_mode_at`,
`charging_seconds`, `non_charging_seconds` (charging.prisma:293-297) — and that row is
deleted at session end. Verified in code, not from the schema comment:
[zaptec-state-event.ts:141-154](apps/api/src/routes/internal/zaptec-state-event.ts#L141)
increments the final delta, then calls `liveSession.delete()`. The rolled-up totals leave
the building only as `finalChargingSeconds`/`finalNonChargingSeconds` in a JSON response
body (:160-161) that nothing persists.

And the vendor already supplies the exact timestamps: the Zaptec CDR DTO declares
`ConnectedDateTime` and `DisconnectedDateTime`
([zaptec.ts:372-373](apps/api/src/lib/vendor/zaptec.ts#L372)). Grepping both names across
`apps/api/src` and `src` returns those two declaration lines and nothing else — never read,
never mapped, never stored.

So plug-time is blocked by a missing column and a `DELETE`, not by missing data. That is a
much cheaper fix than "negotiate new telemetry".

### 5. Billing reads still have unscoped org surfaces — VERIFIED TRUE, but the exposure is not what the phrasing implies

Recounted from source. There are **41** `billing.*` gates in `apps/api/src` (a grep returns
43 lines; 2 are comments). Split: 26 `billing.read`, 15 `billing.write`. Exactly **8** pass
`orgIdParam`, all `{ orgIdParam: "orgId" }`, all in two files (`bill-objects.ts`
:70,:124,:137,:153,:203 and `orgs.ts` :286,:298,:314). That leaves **33 of 41 with no
tenant parameter**, and of those 33 only one compensates at the row layer
([billing.ts:178](apps/api/src/routes/admin/billing.ts#L178) `GET /tariffs`, which calls
`resolveOrgScope` at :180 and filters at :186).

Worst concrete surfaces opened and read:

- [billing.ts:115](apps/api/src/routes/admin/billing.ts#L115) `GET /sessions` builds its
  `LedgerScope` from raw query params via `scopeFromQuery` (:57-67) with no validation, so
  `?orgId=<any-uuid>` reads any tenant's ledger.
- [billing.ts:88](apps/api/src/routes/admin/billing.ts#L88) and :103 read a session by bare
  id (`session-detail.ts:54`, `session-full-detail.ts:152` — `where: { id: sessionId }`),
  with :103 additionally serving raw OCMF/723 blobs on `?include=raw`.
- `billing-cost-centers.ts:34`, `billing-summary.ts:38`, `billing-enrichment.ts:51` and
  `agreements-debug.ts:173` fan out platform-wide by construction.

**The correction to the phrasing.** Because an omitted `orgIdParam` makes
`requirePermission` resolve `orgId = null` and skip `getActiveMembership` entirely
([require-permission.ts:70-75](apps/api/src/lib/auth/require-permission.ts#L70)), these 33
gates are *unreachable by an org member holding `billing.read`*. They are
platform-grant-only. So the defect is **not** "a host reads another host's data". It is:
every platform-grant holder — including `auditor`, `sales_cs` and `finance_internal` via
the `platform.tenant.read` expansion at
[effective-permissions.ts:148-150](apps/api/src/lib/auth/effective-permissions.ts#L148) —
reads every tenant's money data with no scope and no audit row. That is a smaller blast
radius and a worse accountability story than the original claim.

**Support context is shadow-only.** It exists in three places and enforces in none:
`observeSupportContext` (require-permission.ts:132-149) `console.warn`s and returns;
`org-scope.ts:59-69` grants `{ all: true }` unconditionally when
`viaPlatform.includes("platform.tenant.read")`, also after a warn; and
`expandPlatformTenantVerbs` (effective-permissions.ts:125-162) is what hands staff the
per-tenant verbs in the first place. `SUPPORT_CONTEXT_REQUIRED` is declared at
require-permission.ts:109 and referenced nowhere else. No `support_contexts` table exists.
The warnings go to `console`, not `audit.actions`, so there is **no queryable record of any
cross-tenant billing read**.

### 6. DSO/rate definitions can leak cross-tenant or global data — VERIFIED TRUE, with a distinction the phrasing collapses

Two different things are called "DSO/rate definitions" and they behave differently.

**(a) Global by design, correctly.** `billing.cost_factors`
([commercial.prisma:105-120](prisma/schema/commercial.prisma#L105)),
`agreements.cost_factors` (:429-445) and `agreements.rate_references` (:450-471) have no
`org_id` column — they are genuinely national catalogues. `billing-cost-factors.ts:40`,
`billing-rate-references.ts:45/66/80` and `billing-electricity.ts:21` returning everything
is right.

**(b) Leaks anyway.** The DSO route does not stop at the global table:
[billing-dso.ts:36](apps/api/src/routes/admin/billing-dso.ts#L36) →
`repositories/billing-dso.ts:61-70` eagerly includes
`tariffDefinitions: { include: { organization } }`, and `TariffDefinition` **is** per-tenant
(commercial.prisma:124-126, `org_id NOT NULL`). So `GET /api/admin/billing/dso` returns
every tenant's DSO tariff names and org display names through a global-catalogue endpoint.
Same shape at `billing-electricity.ts:21` (per-org usage counts) and
`billing-tariff-detail.ts:29`, where `getTariffDetail(db, tariffId)` keys on id alone and
returns the owning org plus 30 days of that org's `session_ledger` rows.

**And on the write side, which the finding does not mention:**
[billing-tariff-mgmt.ts:44](apps/api/src/routes/admin/billing-tariff-mgmt.ts#L44) takes
`orgId` from the request **body** (`lib/billing/tariff-zod.ts:58-60`) under a gate with no
`orgIdParam`, so a priced tariff can be authored into any organisation. And
[sites.ts:63](apps/api/src/routes/admin/sites.ts#L63) `PATCH` accepts `dsoTariffId` and
passes it through blind (`repositories/sites.ts:116-128`) with no check that the tariff
belongs to the site's org.

### 7. Delivery log has no durable provider-proof chain — VERIFIED TRUE

No table stores a provider message id. Grepping `prisma/schema/*.prisma` for
`provider_message_id|message_id|resend|delivered_at|sent_at|delivery_status` returns
**zero** rows; the only model matching email/delivery/message/notification/statement/invoice
by name is `OrgEmailDomain` (identity.prisma:706), a domain allowlist.

`sendEmail` returns `{ ok: true, id }`
([email.ts:100](apps/api/src/lib/email.ts#L100)) and all **8** call sites drop it:
`org-invites.ts:120-141` echoes it into a 201 body nobody stores; `host-applications.ts:134-136`
and `registration.ts:265` summarise it into a response; `registration.ts:592` and
`driver-access-requests.ts:648,767` ignore it; and `driver-access-requests.ts:289-299` and
:314-322 hang a `.catch()` off a function that cannot throw, so `{ ok: false }` is
unreachable by construction and the outcome is discarded.

**The working comparison exists in the same codebase.** `ocpp.outbound_commands` carries
`status`, `attempts`, `not_before`, `last_attempt_at`, `correlation_id` and a `result`
JSONB (protocol.prisma:96-121); `dispatcher.ts:54-71` claims a row with a single atomic
`UPDATE ... WHERE id = $1 AND status = 'pending' RETURNING`, so a duplicate queue delivery
claims nothing. `delivery-log.ts`'s three-way outcome mirrors `DispatchResult` deliberately
and adds `not_configured` — and the asymmetry it warns about is real:
[email.ts:45-51](apps/api/src/lib/email.ts#L45) **fails open** when `RESEND_API_KEY` is
absent, so a statement "delivered" with no provider configured is today indistinguishable
from one that reached the customer.

### 8. Idempotency keys lack TTL / purge / route scope — NARROWED (one half is false, the other half is worse)

Exactly one general mechanism exists: `events.idempotency_keys`
([apps/api/prisma/schema/platform.prisma:92-102](apps/api/prisma/schema/platform.prisma#L92)),
composite PK `@@id([scope, key])`, `result` JSONB, `expires_at`, `@@index([expiresAt])`.

- **8a — TTL is written. This half of the finding is FALSE.** `expires_at` is populated on
  every insert: `events-repository.ts:49` defines `IDEMPOTENCY_TTL_MS = 7*24*60*60*1000`
  and :159 writes it; `lib/db/raw.ts:381` redeclares the identical constant and :303 writes
  it. (The constant is duplicated in two files rather than shared.)
- **8b — TTL is never enforced. Worse than claimed.** No reader compares `expires_at` to
  `now()`. `events-repository.ts:103-113` matches on `scope_key` only and returns the
  cached result if `existing && existing.result`, regardless of expiry.
  `raw.ts:264-269` selects `WHERE scope = $1 AND key IN (...)` with no expiry predicate. A
  row past its TTL suppresses a replay **permanently**; the column and its index are
  decorative.
- **8c — No purge exists. TRUE.** Nothing deletes from the table. The cron
  (`index.ts:354-413`) runs `sweepStuckPending`, `ensureForwardPartitions`,
  `dropExpiredPartitions`, the Zaptec sync and the agreements billing tick — none touch it.
  The retention list at `partition-cron.ts:220-227` is `events.event_log` only. The table
  grows monotonically.
- **8d — Scope is not route-specific. TRUE.** `const IDEMPOTENCY_SCOPE = "ocpp"` is a
  hardcoded literal in both writers (events-repository.ts:44, raw.ts:380). The schema
  comment advertises `ocpp:<identity>`, `api`, `webhook:<partner>`; no code produces any of
  them. The key is always `event.eventId`.
- **8e — No header-based idempotency anywhere.** Grepping `apps/api/src`, `gateway/src` and
  `packages` for an `Idempotency-Key` header read returns **zero** hits. No HTTP route in
  the tree accepts, validates, or stores a client-supplied idempotency key.
- **8f — The Core-billing contract is defined and entirely unwired.**
  `statement-zod.ts:57-60` defines `idempotencyKeySchema` and requires it on four mutation
  schemas. Those routes do not exist, so the protection does not exist at runtime.

Billing-specific idempotency that *does* exist, all outside that table: `ImportedCdrRef`
`@@unique([sourceKind, sourceCdrId])` (the only true DB-level CDR dedupe);
`SessionLedger.sessionId @id`, making the upsert at `zaptec-session-sync.ts:446` safe;
`CostFactor.code @unique`; `AgreementCostFactor.code @unique`;
`CostCenter @@unique([orgId, code])`.

Not "not final" — **there is no persisted statement or export format at all.**
`statement.ts:12` says the module is "deliberately NOT a database writer"; every document

The only shipped surface anyone could call a statement is `GET /api/driver/invoices`
([driver.ts:740-747](apps/api/src/routes/public/driver.ts#L740)), returning a flat array of

(the only `csv` token in the tree is in `lib/oui/oui-table.ts`), and the console has no
download or statement UI.

### 10. No safe write surface for agreement/cost-factor/rate authoring — VERIFIED TRUE; "only a partial one" is the accurate half

**Exists — 14 routes across 4 routers.** Cost factors: `POST /api/admin/billing/cost-factors`
(billing-cost-factors.ts:50), `PATCH /:id` (:97), `POST /:id/deactivate` (:165),
`/:id/reactivate` (:190). Rate references: `POST` (billing-rate-references.ts:99),
`PATCH /:id` (:154), `POST /:id/retire` (:208). Tariff definitions: `POST`
(billing-tariff-mgmt.ts:44), `PATCH /:id` (:71), `/:id/clone` (:122), `/:id/publish` (:149),
`/:id/retire` (:191). Legacy: `PATCH /api/admin/contracts/:id` (contracts.ts:83),
`DELETE /:id` (:110). Plus `POST /api/admin/agreements/sessions/:sessionId/resolve`
(agreements-resolve.ts:27, the only writer of `agreements.billing_lines`) and the
tariff-*binding* writes at sites.ts:63 and installations.ts:86.

**Does not exist.** Grepping `apps/api/src` (excluding `generated/`) for
`(agreement|agreementClause|bearerRule|driverGroup|agreementCostFactor|costCenter).(create|update|delete|upsert|createMany|updateMany|deleteMany)`
returns exactly two hits, both on the **legacy** `Contract` model
(`repositories/contracts.ts:134`, :147). So there is **no API write path at all** for
`Agreement`, `AgreementClause`, `BearerRule`, `DriverGroup`, `AgreementCostFactor`,
`CostCenter`. The entire ADR 0019 agreements ledger — the thing that actually prices
sessions — is read-only over HTTP and must be authored by seed script or direct SQL.

Three further gaps in what does exist:

1. `billing.export` and `tariff.read`/`tariff.write` are in the catalogue
   (`permissions.ts:64-72`) and gate **zero** routes; the authoring routes all reuse
   `billing.write`.
2. None of the 14 writes accepts an idempotency key, and only rate-reference create runs in
   a transaction. `RateReference` has no `@@unique` on `(code, effective_from)`, so a
   retried `POST` silently stages a duplicate rate version.
3. The resolve route's idempotency is a non-atomic count-then-`createMany`
   (`persist.ts:359-364` then :401, no `$transaction`, no unique index), so concurrent calls
   double-write billing lines.

## Findings nobody asked for that block launch anyway

These were found while censusing and are not in the required list. Three of them are
launch blockers.

**A. Double-billing race in the billing-line writer — BLOCKS LAUNCH.**
[persist.ts:359-364](apps/api/src/lib/agreement/persist.ts#L359) guards with
`count({ where: { sessionId } })`, then at :401 does `createMany` — on the bare
`PrismaClient`, **not** inside a `$transaction`, without `skipDuplicates`, and
`AgreementBillingLine` has no unique constraint (only three plain `@@index` entries at
commercial.prisma:788-790). Two concurrent billing ticks for the same session both observe
0 and both insert, duplicating every billing line. `billing-tick.ts:119-121` loops
candidates calling this per session with no locking, so overlapping cron runs share the
window. The header at billing-tick.ts:5 asserts "Idempotent" — true only single-threaded.
`dispatcher.ts:54-71` solves the identical problem correctly, in one statement, in the same
codebase.

**B. Cross-tenant driver attribution in the CDR import path — BLOCKS LAUNCH.**
[zaptec-session-sync.ts:186-189](apps/api/src/repositories/zaptec-session-sync.ts#L186)
resolves the driver with `tx.idToken.findFirst({ where: { value: { in: candidates }, status: 'active' } })`
and **no `orgId` filter**, where `candidates` are Zaptec-supplied strings (UserId,
TokenName, UserUserName, UserEmail). A matching token value in a different tenant attributes
a billable session — and its ledger row's `driverUserId` — to a foreign driver. The adjacent
station lookup (:149-152) is likewise unfiltered, and nothing checks that the resolved
identity's org matches the org owning the credential passed to `syncZaptecSessions`.

**C. The 100× driver-facing money defect is still live on both endpoints `money.ts` names.**
[driver-sessions.ts:93-98](apps/api/src/routes/public/driver-sessions.ts#L93) defines
`minorToIsk` as `return Number(minor)` under the comment "ISK has no minor unit, so minor
=== major". `driver-invoices.ts:66-67` independently does `Number(lc)` and emits it as
`costIsk`. Both are wrong: `compute-session-cost.ts:12-21` fixes minor = 1/100 króna and
`projections.ts:437` persists `costIskMinor` in aurar, which `projections.test.ts:397` pins
at `64988n` for a 649.88 kr session. **Both endpoints render 64,988 kr.** `money.ts:112-115`
supplies the fix and neither endpoint imports it.

**D. Rate lock-in does not hold, and cannot on today's data path.**
`resolve-tariff-chain.ts:125-128` defines `ResolveInput` as `{ siteId; chargingStationId }`
with **no timestamp**, and :190-206/:225-241 read the *current* `Site.dsoTariffId` and
`Installation.retailerTariffId`. `projections.ts:378-381` calls it during the
`session.stopped` projection — at **stop**. So a rate change applied mid-session prices the
whole session on the new binding. Separately, `computeSessionCost` declares `startedAt` and
`stoppedAt` on `SessionInput` (compute-session-cost.ts:69-71) and its body never reads
either — I read the whole function (:112-205) to confirm. `resolve-tariff-chain.ts` loads
`TariffDefinition` by primary key and checks only `status === 'active'` (:299-325); there is
no `validFrom`/`effectiveFrom` predicate in the file.

**E. Two parallel cost-factor tables, easily confused.** `billing.cost_factors` (model
`CostFactor`, commercial.prisma:115-132) and `agreements.cost_factors` (model
`AgreementCostFactor`, :439-449, codes DSO/ELE/ACS/PRM/TRF/SRF/RNT/MTR) are distinct tables
in distinct schemas. `RateReference.costFactorId` points at **AgreementCostFactor** (:474)
while `billing-cost-factors.ts` and `billing-dso.ts` read **CostFactor**. Any reasoning that
treats "the cost factor table" as one thing will be wrong.

**F. Three tenant-scoping conventions coexist in one area**, which is why the gaps are easy
to miss: (a) mandatory positional `orgId` (bill-objects.ts:82/101/118,
org-tariff-chain.ts:44); (b) explicit `orgId: string | null` where null deliberately means
all tenants (billing-contracts.ts:53, billing-driver-contracts.ts:54/139); (c) no `orgId`
parameter at all (billing-summary.ts all five, billing-enrichment.ts:71,
billing-cost-centers.ts:41, billing-tariff-detail.ts:89, session-detail.ts:49,
agreements.ts:155). Convention (c) is correct only for the national catalogues, and those
files say so in their headers; the ledger-derived reads in (c) do not.

**G. `listAgreements` exists twice with different tenancy.** `billing-contracts.ts:53`
takes `(db, orgId: string | null)` and filters; `agreements.ts:155` takes `(prisma)` with no
filter. Also `getContractsTiles(db)` (billing-contracts.ts:116) takes no `orgId` while its
sibling list function does, so tile counts can describe a different population than the list
beneath them.

**H. Two ORMs on the billing read path.** Most repositories use the generated Prisma client,
but `driver-invoices.ts:8-13` and `billing-electricity.ts:86-92` use Drizzle. Driver billing
material and the retailer-rate catalogue read through a different data layer than the rest
of Core billing.

**I. `audit.actions.org_id` carries `onDelete: Cascade`** (platform.prisma:110). Deleting an
org deletes its entire audit trail. The table has exactly one reader
(installation-ocpp.ts:272/:330) and no retention or export route, so the who-did-what log
for a billing tenant is both unreadable in product and destructible by an ordinary org
delete.

## Documentation that this census refutes

Five source headers or prior docs assert something the source does not support. Listed
because each is the kind of line a reader trusts without checking.

## Migration convention, for whoever writes the schema

Drizzle became authoritative on 2026-08-07 (ADR 0051), restated in `FOCUS.md:161-171` and in
a banner at `apps/api/drizzle.config.ts:2-19`. Prisma is explicitly downstream and survives
only to generate a client for ~500 un-ported calls.

**The pattern to match.** Files at `apps/api/drizzle/NNNN_<tag>.sql`: four-digit zero-padded
index, underscore, drizzle-kit's two-word tag. Plain SQL, statements separated by the literal
marker `--> statement-breakpoint`, no transaction wrapper, no prose header. **Two metadata
artifacts must move with it**: `apps/api/drizzle/meta/_journal.json` and one
`apps/api/drizzle/meta/NNNN_snapshot.json`. Produced by `npm run db:generate:sql` **after**
editing `packages/shared/src/db/*.ts`. Hand-writing SQL straight into `apps/api/drizzle/`
without regenerating the snapshot would silently corrupt every future diff.

Latest migration: `apps/api/drizzle/0001_regular_talos.sql` — one line,
`ALTER TYPE "agreements"."RateBasis" ADD VALUE 'per_connector';`, journalled 2026-08-08.

The Prisma directory is legacy and should not be added to. Only the first of its 47
migrations is genuinely Prisma-generated; every one after it is hand-written SQL in a
Prisma-shaped directory.
