## 1. The five findings that should change what happens next

### 1.1 Billed energy is `meterStop`, not `meterStop − meterStart`

`onOcppRawStopTransaction` — the **live** ledger writer — overwrites the
session's energy with the stop reading and prices that number directly:

```
projections.ts:869   energyWh = BigInt(meterStartWh)      // start
projections.ts:928   energyWh = BigInt(meterStopWh)       // stop OVERWRITES
projections.ts:959   energyKwh = Number(updated.energyWh) / 1000
projections.ts:966   computeSessionCost({ …, energyKwh }, chain)
```

No code anywhere subtracts the two. In OCPP 1.6 `MeterStart`/`MeterStop` are
readings of the **cumulative** energy-active-import register, so this is
correct only for chargers that happen to report a per-session value beginning
near zero.

**This is not a confirmed live overcharge** — the observed session costs look
plausible, which suggests the deployed Zaptec fleet reports per-session values.
It is an *unguarded assumption with a catastrophic failure mode*: one charger
reporting a lifetime register bills its whole lifetime as a single session. And
**no test can catch it, because every fixture uses `meterStart: 0`**
(`projections.test.ts:814`).

The check is one query against real sessions — `min/max(energy_wh)` and the
`meterStart` distribution — and it should happen before Core bills anyone.

### 1.2 A ledger row can claim CDR provenance while carrying an OCPP price

`zaptec-session-sync.ts:467-470` updates only `verifiedSource:'cdr'` and
`enrichmentStatus`. `energy_kwh` and `cost_isk_minor` keep the OCPP figures.
The schema comment at `commercial.prisma:314-319` claims the CDR sync "overlays
with the authoritative Zaptec figure". It does not. A Core statement that
trusts `verified_source` is asserting something untrue to a customer.

### 1.3 Two org billing reads are cross-tenant by construction

`listCostCenters(db, year, month)` (`billing-cost-centers.ts:41`) and
`getProjectedOrgRevenue` (`billing-summary.ts:208`) take **no `orgId`**, and
their routes gate on a bare `requirePermission('billing.read')` with no
`orgIdParam`. Any tenant holding `billing.read` sees every tenant's monthly
revenue. The correct shape already exists three files away —
`bill-objects.ts:70` passes `{ orgIdParam: 'orgId' }`.

More broadly: only **32 of 165** `requirePermission` call sites pass
`orgIdParam`, and only **8 of 43** billing gates do. Because
`resolvePermissionsWithProvenance` skips the membership lookup entirely when
`orgId` is null, omitting the param does not merely skip a check — it makes
membership **incapable** of satisfying the verb.

### 1.4 The member-admin carve-out has locked the live operator out of driver management

This is a consequence of my own earlier change, now measured. `MEMBER_ADMIN_VERBS`
(`effective-permissions.ts:110-114`) strips `member.write/invite/remove` from
platform expansion. The live operator holds a `super_user` grant and **no
membership**, so `viaMembership` is empty and every one of these denies:
`admin-users.ts:156,220,238,265` · `admin-id-tokens.ts:63,88,127` ·
`driver-group-memberships.ts:48,156` · `access-requests.ts:90,178` ·
`orgs.ts:242,395`.

The source comment I left at `admin-users.ts:201-204` saying the bootstrap admin
still passes is **stale** — `auth.ts:134-137` mints every cookie with a
`userId`, so `isBootstrapSession` is false and the god-mode branch is dead code
that only honours pre-Sprint-5.5 cookies (expired, 12h TTL).

**Core cannot ship manual driver management until this is resolved.** The fix is
a decision, not a patch: give staff memberships, or add an explicit platform
verb for member administration.

### 1.5 The Core subscription has schema support and no emitter

`RateBasis.per_connector` exists (`commercial.prisma:397-409`) and
`resolve.ts:248-252` throws *"per_connector is not resolvable from a session —
it is billed by the flat-fee feeder"*. **The flat-fee feeder does not exist**;
grep finds only the enum, the throw, its test and a comment.

`computeCoreSubscription` in this commit is that feeder's calculation core.

## 3. Core V1 rate policy — recommendation

**`start_rate`.** The version in force when the session started prices the whole
session.

Not because it is simplest. Because the alternatives cannot be computed
honestly on this system's data:

- **`split_by_time`** apportions *energy* by *time*, which is right only if
  power is constant. Real charging tapers, so a session crossing midnight
  usually consumed most of its kWh before the boundary. Doing it properly needs
  interval energy — and `charging.meter_values` is empty by construction (C5),
  while `live_session_samples` is a live-view sampler whose only writer was
  parked on 2026-08-02.
- **`highest_rate`** is defensible only as a deliberate commercial choice, never
  as a default.

`start_rate` also matches `pickActiveRate`, which already selects one rate per
session. All three are implemented; `crossedBoundary` is reported under each, so
the exposure is measurable rather than invisible.

On one 10 kWh session crossing a rate change the three policies differ by
**13.60 kr** — asserted in `rate-window.test.ts`.

## 5. Decisions needed from Andri

1. **Zero connectors, N drivers → 0 kr.** The cap is per connector, so with no
   connectors the cap is zero. Implemented literally and pinned by a test. If
   Core should bill drivers in that state, the frame needs a floor.
2. **Plug-time grace anchor.** Default implemented is `charging_end` (bills only

## C01 — Sessions, CDRs and session records

There is no single "CDR of record". `charging.sessions` is one row per physical session written by four independent writers (OCPP raw-frame projections, the Zaptec `/chargehistory` poll importer, the Zaptec `/session-end` webhook, and the AMQP StateId-723 handler), and `reports.session_ledger` is the priced mirror written by three of those four. The ENRICH-1 per-source columns (`ocpp_energy_kwh`, `cdr_energy_kwh`, `amqp_energy_kwh`) record what each feed claimed, but the ledger's `energy_kwh` and `cost_isk_minor` are written once on first arrival and never recomputed — the CDR overlay flips `verified_source` to `"cdr"` while leaving the OCPP energy and OCPP-derived price in place. `charging.imported_cdr_refs` is the only place a vendor CDR payload survives verbatim, and it is Zaptec-only. Nothing anywhere models plug time, idle time, grace periods or a billable-session predicate as durable data; the only charge/idle split is derived at read time from an OCMF blob and thrown away.

**Area findings**

1. The CDR overlay never restates the price. `apps/api/src/repositories/zaptec-session-sync.ts:446-471` upserts the ledger with the CDR energy and CDR-derived cost only in the `create` branch; the `update` branch writes exclusively `verifiedSource: "cdr"` and `enrichmentStatus`. When the OCPP path already wrote the row (`projections.ts:980-1002`), the CDR sync rewrites `charging.sessions.energy_wh` and `cost_inc_vat_minor` at :306-332 but leaves `reports.session_ledger.energy_kwh` and `cost_isk_minor` at the OCPP figures. The row then claims CDR provenance while carrying an OCPP price. Any Core statement that trusts `verified_source` will be wrong by exactly the drift the system already knows how to measure.

2. `charging.sessions` has NO `stopped_at` column — the seed path is inaccurate. The canonical end timestamp is `ended_at` (`apps/api/prisma/schema/charging.prisma:33`); `ocpp_stopped_at` and `cdr_stopped_at` :116-117 are per-source mirrors, and `stopped_at` exists only on `reports.session_ledger` (`commercial.prisma:315`). There is no third mirror for the AMQP feed even though `amqp_energy_kwh` exists.

3. ## C02 — Price calculation: legacy tariff path

All four seed paths exist. The price of record is a two-component, flat-per-kWh, single-VAT-line engine: `resolveTariffChainWithIdsForSession` reads exactly one DSO tariff off `Site.dsoTariffId` and one retailer tariff off `Installation.retailerTariffId`, and `computeSessionCost` multiplies total session kWh by the summed ex-VAT rate in BigInt aurar, then adds one VAT line at the bottom. There are no time windows, no split periods, no per-minute or per-session basis, no start-vs-during distinction and no subscription math anywhere in this path — the rate is resolved at session-STOP time from whatever row is `status='active'` right then, and `TariffDefinition.validFrom` / `validUntil` are never read by the resolver. Against the Core frame this covers the DSO and retailer energy rates only; the connector/driver subscription with the 450 kr cap, plug-time fee, CPO margin, adjustment lines and period lock have no implementation here at all.

**Area findings**

1. The tariff write API and the pricing engine disagree on the `computeRule` discriminator, so any tariff created through the product is unpriceable. `ComputeRuleSchema` accepts only `flat_per_kwh` and `flat_per_session` (`apps/api/src/lib/billing/tariff-zod.ts:31-50`), `createTariff` persists that object verbatim (`apps/api/src/repositories/billing-tariff-mgmt.ts:130`), and `parseComputeRule` accepts only `kind === "flat"` and otherwise throws `compute_rule_unsupported` (`apps/api/src/lib/tariff/resolve-tariff-chain.ts:90-122`). Every fixture and test in the repo uses `{ kind: "flat", pricePerKwhMinor: … }`; nothing uses `flat_per_kwh`. Publish such a tariff, bind it, and every session at that site fails to price and the queue retries forever. `flat_per_session` has no engine implementation at all.

2. `onSessionStopped` — the handler every doc comment calls the price of record — is registered but unreachable. `registerProjection("session.stopped", onSessionStopped)` at `apps/api/src/lib/ocpp/projections.ts:1039`, and the file's own comment at `:1046-1051` states no translator emits the domain events; a grep for `session.stopped` across `apps/api/src` and `gateway/src` finds only the registration, the tests and comments. The live OCPP pricing writer is `onOcppRawStopTransaction` (`projections.ts:887-1013`). A Core implementer reading `onSessionStopped` will port dead code and miss the live one.

3. No code path computes `meterStop - meterStart`. `onOcppRawStartTransaction` writes `energyWh: BigInt(meterStartWh)` (`projections.ts:869`), `onOcppRawStopTransaction` overwrites it with `energyWh: BigInt(meterStopWh)` (`projections.ts:928`) and then prices `Number(updated.energyWh) / 1000` (`projections.ts:959-960`). The legacy `onSessionStopped` does the same at `:344` and `:383-384`. Every test fixture sets `meterStart: 0` (`projections.test.ts:814`), so the suite cannot catch it. Only the CDR path is safe, because it uses the vendor's per-session `z.Energy` (`zaptec-session-sync.ts:195`).

4. The authoritative CDR figure never corrects an already-priced ledger row. `zaptec-session-sync.ts:228-235` re-resolves the chain and recomputes `breakdown` from the CDR energy, but the upsert's `update` branch at `:467-470` writes only `verifiedSource: "cdr"` and `enrichmentStatus` — `costIskMinor` and `energyKwh` are omitted, so the OCPP-derived price stands even when `enrichmentStatus` is set to `"mismatch"`. The recomputed `breakdown` is returned to the caller and otherwise discarded.

5. Rate versioning is columns-only. `TariffDefinition` carries `validFrom` and `validUntil` and is indexed on `[orgId, costFactorId, validFrom]` (`prisma/schema/commercial.prisma:132-152`), but `loadTariffDefinition` selects neither and gates solely on `status !== "active"` (`resolve-tariff-chain.ts:303-325`). `publishTariff` does not chain-retire the prior version — the TODO at `billing-tariff-mgmt.ts:247-249` and `:274-275` says `family_code` does not exist — so two rows for the same rate can both be `active`, and which one prices a session depends on which UUID the Site FK happens to hold.

6. Rounding is per component, not on the total, and VAT is a single bottom line. `(milliKwh * pricePerKwhMinor + 500n) / 1000n` runs once per component (`compute-session-cost.ts:158-159`), the results are summed, and VAT is then `(subtotal * vatRateScaled + 500_000n) / 1_000_000n` (`:178-181`). A per-line-VAT reimplementation will not reproduce these totals; `shadow-compare.ts:80-83` already bakes in a 1-aurar tolerance to paper over exactly this difference.

7. `retireTariff` is a live-fire hazard. It counts bindings across Site (five FK columns), Installation, ChargingStation and DriverContract and returns them as a warning string, but performs the update unconditionally (`billing-tariff-mgmt.ts:326-380`). Because `loadTariffDefinition` throws `tariff_definition_inactive` on any non-`active` status (`resolve-tariff-chain.ts:320-325`), retiring a bound DSO tariff stops all pricing at those sites and, inside the projection, rolls back the whole `session.stopped` transaction on every retry.

8. Contradiction to the KNOWN FACTS block: `contract.write` and `tariff.write` guard zero routes, but tariff writes are not ungoverned — the five mutation routes in `apps/api/src/routes/admin/billing-tariff-mgmt.ts:42-191` are each guarded by `requirePermission("billing.write")`, and the read routes by `billing.read`. The unused permission strings are the dead ones, not the surface.

9. There are exactly four call sites of the engine in production code and they must be changed together: `projections.ts:377` and `:954`, `zaptec-session-sync.ts:228`, and `routes/webhooks/zaptec.ts:370`. Two more live in `apps/api/scripts/backfill-session-costs.ts:139` and `shadow-compare-resolvers.ts:188`. Only `zaptec-session-sync.ts` and `webhooks/zaptec.ts` have `.test.ts` neighbours that exercise a real price; `webhooks/zaptec.test.ts:346` asserts the canonical `64988`.

**Area findings**

1. `apps/api/src/lib/agreement/persist.ts:231-243` concatenates the clauses of the installation agreement **and** every matching workplace agreement into one flat `ClauseInput[]` with no dedupe, and `packages/commercial/src/agreement/resolve.ts:36` emits lines for every entry. The `@@unique([agreementId, costFactorId])` on `AgreementClause` (`prisma/schema/commercial.prisma:533`) only prevents duplicates *within* one agreement. If an installation agreement and a workplace agreement both enlist `DSO`, the session is billed for DSO twice. No test covers the two-agreement case — `resolve.test.ts` "two enlisted factors emit independent lines" (:463) uses two *different* factors.

2. `apps/api/src/lib/agreement/persist.ts:293` sets `ctx.agreementId = installationAgreement?.id ?? ""`, and `:401-408` stamps that value on every inserted row. `loadAgreementContext` can return `granted: true` with `installationAgreement === null` — the membership test at `:200` is satisfied by `workplaceAgreements.length > 0` alone. That path inserts `agreementId: ""` into a `@db.Uuid` FK column and will fail at runtime. On the path that does have an installation agreement, lines derived from a *workplace* agreement's clauses are still stamped with the installation agreement's id, so line provenance is wrong by construction.

3. `apps/api/src/repositories/billing-rate-references.ts:141-143` assigns `g.current = row` unconditionally while iterating rows ordered `code asc, effectiveFrom desc`. With two overlapping current rows for one code, the *last* one iterated wins — the OLDER row. `pickActiveRate` (`packages/commercial/src/agreement/resolve.ts:135`) sorts `effectiveFrom` desc and picks the NEWER. The operator console and the resolver will name different rates as current, and nothing logs it. The `// There should be at most one current row per code (enforced at write)` comment at :142 is not true: enforcement covers only the already-active row, not two staged rows.

4. `retireRateReference` (`billing-rate-references.ts:367-370`) writes `effectiveUntil = now()` on a `current` row, which is exactly the mutation `patchRateReference:312-314` refuses as `active_row_immutable`. Both routes sit behind the same `billing.write` permission (`routes/admin/billing-rate-references.ts:154` and :208), so Rule 5 is a speed bump, not an invariant. Core's replay guarantee needs the constraint in the database or in one shared function.

5. `packages/commercial/src/agreement/types.ts:34-37` states the Postgres enum `agreements."RateBasis"` does NOT carry `per_connector`. `apps/api/drizzle/0001_regular_talos.sql` is a one-line `ALTER TYPE "agreements"."RateBasis" ADD VALUE 'per_connector';`. Adding a resolver test to the wrong file silently gets you nothing.

## C04 — DSO, electricity retailer and CPO margin rates

Two disconnected rate stacks exist. The one that actually prices sessions is `billing.tariff_definitions` rows bound to `Site.dsoTariffId` and `Installation.retailerTariffId`, resolved by `resolveTariffChainWithIdsForSession` into exactly two additive per-kWh components (dso plus retailer) with one uniform VAT rate — there is no margin component in it, and no code path ever constructs the `platform_fee` kind the engine declares. The second stack is the versioned rate book `agreements.rate_references` plus `agreements.agreement_clauses.allocation_json`, which is the only place a CPO margin is modelled at all (as `allocation.markup`), and it has full CRUD for the rate rows but zero write surface for the allocation that carries the markup. Core's network-plus-energy-plus-margin stack therefore has network and energy in one system, margin in another, and no code that combines all three.

**Area findings**

1. **The tariff write API produces rows the pricing engine cannot read.** `apps/api/src/lib/billing/tariff-zod.ts:47-50` accepts `computeRule.kind` of `flat_per_kwh` or `flat_per_session`, and `createTariff` stores it verbatim (`apps/api/src/repositories/billing-tariff-mgmt.ts:130`). The resolver accepts only `kind === "flat"` (`apps/api/src/lib/tariff/resolve-tariff-chain.ts:90-122`) and throws `compute_rule_unsupported` otherwise; `apps/api/src/repositories/org-tariff-chain.ts:155` also returns null for anything but `"flat"`. The seed that produced the live rows writes `{ kind: "flat", pricePerKwhMinor: 864 }` (`apps/api/scripts/seed-dalvegur-n1-contract.ts:97`). So every tariff authored through the admin console and published is a session-stop failure waiting on the next session at that site. Fix one vocabulary before any Core rate authoring ships.

2. **`per_connector` exists in both ORMs and in neither database.** `prisma/schema/commercial.prisma:406` and `packages/shared/src/db/commercial.ts:46` declare it; `prisma/migrations/20260508120000_agreements_v2/migration.sql:77-82` creates the enum with four values and no later migration alters it. `CreateRateReferenceSchema.basis` (`apps/api/src/lib/billing/rate-reference-zod.ts:33`) also omits it. The Core connector subscription cannot be stored as a rate row until an `ALTER TYPE` lands.

3. **Someone has already landed the Core subscription and plug-time math in this worktree, unwired.** `packages/commercial/src/core-billing/subscription.ts` implements 200 plus 50 capped at 450 exactly (`CORE_CONNECTOR_PRICE_MINOR = 20_000n` :43, cap logic :129-131) with `subscription.test.ts` beside it, and `core-billing/plug-time.ts` implements the grace-period fee. Neither is exported from `packages/commercial/src/index.ts` or `packages/commercial/package.json` `exports`, and `grep -rn "core-billing"` finds zero importers. `plug-time.ts` has no test file. Treat these as drafts to wire, not as shipped behaviour.

4. **The retailer half of every price is computed and then thrown away.** `apps/api/src/lib/ocpp/projections.ts:443` writes `tariffDefinitionId: resolved.dsoTariffDefinitionId` and the comment above it states the retailer id is deliberately not persisted. `reports.session_ledger` has one `costIskMinor` and no line items. A CDR-backed driver statement showing "network X, energy Y" cannot be reconstructed from the ledger — only from re-resolving today's tariffs, which is wrong for any historical month.

5. **Contradicts KNOWN FACTS: a vitest step IS wired into CI.** `.github/workflows/check.yml:91` is `- run: npm test` with `CI: "true"`. The practical effect still matches the stated fact, but for a different reason: line 70 runs `npm run check`, and the file's own comment (:86-90) records that `check:work-view` compares a page that no longer exists, so the job fails before reaching the test step. `vitest.config.ts:19-24` does include `packages/**/*.test.ts`, so the commercial resolver tests would run if the job got that far.

6. **A documented column does not exist.** `apps/api/src/repositories/billing-rate-references.ts:13-14` states "Phase 4 will add pattern_json … The column is in the schema; this repo ignores it." `grep -rn "pattern_json"` across the repo hits only that comment and the twin in `rate-reference-zod.ts:13-14`. There is no `pattern_json` in the Prisma model, the drizzle table or any migration. Any Core plan that assumes time-of-day restrictions are half-built is wrong.

7. **`retireTariff` will happily break live pricing and only warns.** `apps/api/src/repositories/billing-tariff-mgmt.ts:326-384` counts bindings across eight FK columns, retires the row regardless, and returns a warning string ending "Sessions resolving through these anchors will now fail to find an active tariff." Combined with `loadTariffDefinition` rejecting any status other than `active` (`resolve-tariff-chain.ts:320-325`), one admin click takes a site offline for billing at the next session stop. Core's period-close design needs to gate this, not just narrate it.

8. **`tariff.write` guards nothing; `billing.write` guards everything rate-shaped.** `apps/api/src/lib/auth/permissions.ts:69` and `:152` are the only two occurrences of the string. All fourteen rate and tariff write routes gate on `requirePermission("billing.write")`. `FINANCE_BUNDLE` (:171-179) carries `billing.write` without `tariff.write`, so the intended separation between "can invoice" and "can set prices" is not enforced anywhere.
## C05 — Driver statements, org billing material, export, delivery log

A "driver statement" today is one JSON array: `GET /api/driver/invoices` returns the driver's own `charging.sessions` rows with a single VAT-inclusive total per session, taken from `reports.session_ledger.cost_isk_minor` when present. There is no period grouping, no per-cost-factor line breakdown, no invoice number, no issue date and no persisted statement anywhere — the archived operator console did the month grouping in React and back-computed ex-VAT by dividing the gross by 1.24. There is no org billing export of any kind (no `Content-Disposition`, no CSV, no PDF, no R2 write in any billing path), no period close or lock (`reports.billing_period_summary` was dropped 2026-08-07), no correction or adjustment write surface, and no delivery log — `sendEmail` returns a Resend id that is echoed in one HTTP response body and then discarded.

**Area findings**

1. Every seed path exists except two, and both absences are load-bearing: there is no `apps/api/src/routes/admin/billing-summary.ts` problem (it exists at :36), but `apps/api/src/repositories/billing-summary.ts` is a Prisma dashboard repo, not an invoice repo, and there is no billing-export module of any kind anywhere in the tree — zero matches for `Content-Disposition`, `text/csv` or `application/pdf` outside `node_modules`. The org "export" in the Core frame is fully greenfield.

2. `packages/commercial/src/core-billing/` contradicts the working assumption that Core pricing is greenfield: `subscription.ts:118` `computeCoreSubscription` already implements 200 plus 50 capped at 450 exactly, and `plug-time.ts:56` implements the grace-period fee. Both are UNTRACKED (`git status --porcelain` reports `?? packages/commercial/src/core-billing/`), absent from `packages/commercial/src/index.ts:15-16`, and have zero importers — and the directory grew a fourth file between two reads during this census, so it is being written concurrently. Treat as in-flight work product, not as committed source.

3. `RateBasis.per_connector` was added to the enum on 2026-08-08 (`prisma/schema/commercial.prisma:397-409`) and `packages/commercial/src/agreement/resolve.ts:248-252` throws `per_connector is not resolvable from a session — it is billed by the flat-fee feeder`. The flat-fee feeder does not exist: grep for `per_connector` across `apps`, `packages` and `scripts` returns only the enum, the throw, its test, and a comment. The schema is ready for the Core subscription and the emitter is missing.

4. The CDR overlay is a lie in the current code. `apps/api/src/repositories/zaptec-session-sync.ts:467-470` sets only `verifiedSource: "cdr"` and `enrichmentStatus` in the upsert's `update` branch, so an existing OCPP-written ledger row keeps its OCPP `energy_kwh` and `cost_isk_minor` while being relabelled as CDR-verified. This directly contradicts `prisma/schema/commercial.prisma:314-319`, which states the CDR sync "overlays with the authoritative Zaptec figure". A Core statement that trusts `verified_source` would be wrong.

5. Both ledger writers deliberately refuse to restate. `apps/api/src/lib/ocpp/projections.ts:450-456` and :1001 set `update: { stoppedAt }` only, with the comment "prefer not to overwrite a settled cost". That is the closest thing to immutability the system has, and it is per-row and accidental — it protects against replay, not against a period being reopened, and it also means a genuinely wrong cost can never be corrected in place. Core needs an explicit adjustment line, which `AgreementBillingLine.billableEventType` anticipates at `commercial.prisma:761-763` and nothing implements.

6. `billing.export` joins `contract.write` and `tariff.write` as a declared permission guarding zero routes (`apps/api/src/lib/auth/permissions.ts:66`, granted in bundles at :166 and :173, expanded as a WRITE verb in `effective-permissions.ts:139`). Additionally `platform.finance.read`, `platform.finance.write` and `audit.read` guard zero routes. Only `billing.read` (28 call sites) and `billing.write` (15) are live.

7. The two org-level billing reads are cross-tenant by construction, not by permission bug: `apps/api/src/repositories/billing-cost-centers.ts:41` takes `(db, year, month)` with no orgId and its route at `routes/admin/billing-cost-centers.ts:32` calls `requirePermission("billing.read")` with no `orgIdParam`; `getProjectedOrgRevenue` at `billing-summary.ts:208` behaves the same through `routes/admin/billing-summary.ts:36`. Any tenant finance user with `billing.read` sees every tenant's monthly revenue. The correct pattern already exists three files away at `routes/admin/bill-objects.ts:70`.

8. `driver-invoices.ts:83` populates the field named `billingHomeName` from `organizations.displayName`, bypassing the entire ADR 0029 BillObject spine that `commercial.prisma:581-590` says resolves the invoice recipient. Combined with `whToKwh` at :28 rounding kWh to one decimal against the ledger's `Decimal(10,3)`, the current statement gets both the payer and the quantity wrong before any pricing question is asked.
## C06 — Plug time, idle time, occupancy and grace periods

No time-based fee is charged anywhere today: every priced path multiplies energy only, and the word "grace" does not appear in a single source file under `apps`, `packages`, `src` or `prisma` (the only hits are "gracefully" in shutdown handlers and one out-of-scope comment in `compute-session-cost.ts:35`). Plug time is nonetheless *measured* in two disconnected places — `charging.live_sessions.charging_seconds` / `non_charging_seconds`, maintained by the Zaptec AMQP state handler and then **deleted with the row at session end**, and a read-time `chargeTimeSec` / `idleTimeSec` split derived from OCMF or EnergyDetails intervals in `session-detail.ts`, which is display-only. The plumbing that *would* carry a plug-time fee already exists — `RateBasis.per_minute`, `basisQuantityFor`, `agreements.billing_lines.basis_type` / `basis_quantity`, and seeded factor codes `TRF_IDLE` / `TRF_PLUG` — but nothing computes plug minutes, nothing applies a grace threshold, and the only per-minute quantity any resolver can see is `endedAt - startedAt`, i.e. charge time, not plug time.

**Area findings**

1. **Plug time is measured and then deliberately thrown away.** `apps/api/src/routes/internal/zaptec-state-event.ts:156-162` returns `finalChargingSeconds` and `finalNonChargingSeconds` in the JSON response and `:153-155` deletes the `live_sessions` row in the same request. No column on `charging.sessions` or `reports.session_ledger` receives them. Making plug time billable is therefore not a measurement problem — it is a five-line persistence problem plus a destination column.

2. **`compute-session-cost.ts` takes the timestamps and never reads them.** `SessionInput.startedAt` / `stoppedAt` at `apps/api/src/lib/tariff/compute-session-cost.ts:65-73` are documented as unused, and the body (`:112-205`) touches only `energyKwh`. The docstring at `:105` also claims the function throws on a "non-flat tariff component" — it does not; that check lives upstream in `resolve-tariff-chain.ts:121`. Anyone reading the docstring alone would assume a guard that is not there.

3. **The plug-time data source is parked infrastructure.** `apps/api/src/routes/internal/zaptec-state-event.ts` is the only writer of both `charging.live_sessions` and `charging.live_session_samples`, and it is fed exclusively by the Zaptec Service Bus consumer that `docs/notes/2026-08-03-park-the-azure-bus.md` decided to park (StateId 513 stale since 2026-07-31, 723 never arrived, `ev_plc_mac` 0 of 1,603 sessions). This qualifies the KNOWN FACT that telemetry "lands in charging.live_session_samples" — that was true up to 2026-08-02 and is no longer true after the parking decision.

4. **OCPP StatusNotification is a durable, indefinitely-retained plug-state source and nobody bills on it.** `gateway/src/identity-do.ts:232-244` classifies `StatusNotification` as `operational`, and `apps/api/src/lib/db/partition-cron.ts:191-197` gives `operational` a `null` (indefinite) Postgres window while only `raw_protocol` expires at 7 days. So Preparing / Charging / SuspendedEV / Finishing / Available transitions are permanently in `events.event_log` with `occurredAt`. That is the honest basis for plug time on OCPP-terminated chargers, and it is exactly what ADR 0049's sequencing step 3 proposes. The projection at `projections.ts:765-812` currently discards the history by overwriting `Connector.status` in place.

5. **A per-minute rate would today bill charge time under the name "time".** `packages/commercial/src/agreement/resolve.ts:230` maps `per_minute` to `ctx.durationMinutes`, and `apps/api/src/lib/agreement/persist.ts:368-370` derives that solely from `endedAt - startedAt` on `charging.sessions` — the StartTransaction-to-StopTransaction window. There is no idle quantity and no plug quantity on `SessionContext` (`packages/commercial/src/agreement/types.ts:148-167`). Enabling `per_minute` without first landing a plug-time quantity produces a plausible-looking but wrong invoice line.

6. **The pilot gate is internally inconsistent on time fees.** `apps/api/src/lib/billing/pilot-scope.ts:15-24` admits factor codes `TRF_CHG`, `TRF_IDLE` and `TRF_PLUG`, while `:27-31` restricts compute-rule kinds to `flat_per_kwh` and `flat_per_session`. An operator can create an idle-fee cost factor that no permitted compute rule can price. Meanwhile `rate-reference-zod.ts:33` accepts `per_minute` on the write API with no downstream consumer, and `driver-pricing.ts:229` will publish the resulting `perMinuteMinor` to drivers.

7. **The two Prisma schema copies disagree on `RateBasis`.** `prisma/schema/commercial.prisma:397-401` lists four bases; `apps/api/prisma/schema/commercial.prisma:407-419` lists five, adding `per_connector` with a comment dated 2026-08-08 pointing at the flat platform fee. Any plug-time work that touches `RateBasis` must decide which copy is authoritative first.

8. **The idle heuristic is a duplicated magic number.** `deltaKwh > 0.001` appears at `apps/api/src/lib/ocmf.ts:227` and again at `apps/api/src/repositories/session-detail.ts:235`, and the summation loop over it is copy-pasted at `session-detail.ts:142-145` and `session-full-detail.ts:305-306`. None of the three files has a test. If Core bills on idle minutes, this threshold becomes a money constant and needs one home plus coverage.

9. **`session_ledger.durationSec` is a misleading name for billing purposes.** It is written from `stoppedAt - startedAt` at `projections.ts:387-390`, at `projections.ts:962-964` on the raw path, and at `zaptec-session-sync.ts:197-200` on the CDR path — three writers, all charge-window, none plug-window. A Core implementer reaching for "the duration we already store" will silently get the wrong quantity.
## C07 — Driver management, access groups, invite paths

Six distinct paths create a driver or grant access today, and they do not agree with each other: self-registration (`registerDriver`), the platform admin user create (`createUser`), the operator org invite (`createInvite` plus `/api/public/invites/consume`), the host driver invite (`createDriverInvite` plus `/api/driver/claim-invite` and `/api/driver/redeem-invite`), the email-domain `auto_join` grant inside `consumeEmailVerification`, and the operator-reviewed access request (`createSelfRequest` plus `approveRequest`). `createDriver` in `apps/api/src/repositories/create-driver.ts` was written to be the single source of truth for all of them and has **zero call sites** — the drift it exists to prevent is still live, and one path (`createDriverInvite`) creates a driver User with no IdToken at all, so an invited driver cannot be authorised at a charge point even after redeeming. The access primitive Core needs — the access group — is `agreements.driver_groups`, and nothing anywhere in `apps/api/src` creates, renames or deletes one, nor removes a member from one: groups are read-only fixtures seeded by hand, hung off an Agreement by a NOT NULL FK.

4. `apps/api/src/routes/public/driver.ts:1089` guards claim with `if (row.user.credentials !== null)`. `credentials` is `UserCredential?` (`prisma/schema/identity.prisma:73`), a to-one relation, so this is a ROW-existence test. `clearUserPasswordHash` (`apps/api/src/domains/identity/repositories/users.ts:381`) sets `passwordHash` to null and keeps the row. An admin password clear therefore locks that driver out of claiming forever. `apps/api/src/routes/public/invites.ts:162-167` names this exact defect in `driver.ts` and does the column test instead — the fix is a two-line port, not a design question.

5. Nothing in `apps/api/src` writes to `agreements.driver_groups` — no `driverGroup.create`, no `insert(driverGroups)`. `GET /api/admin/groups` (`apps/api/src/routes/admin/groups.ts:18`) returns family groups and vendor user groups only. 6. `consumeEmailVerification` (`apps/api/src/repositories/registration.ts:465`) grants a `driverGroupMembership` automatically on `auto_join`, with a non-idempotent Prisma `create` — a driver already in that group (via invite or manual add) who then verifies their email hits a unique-constraint 500 rather than a no-op. 7. `approveRequest` (`apps/api/src/repositories/driver-access-requests.ts:549-572`) chooses the destination access group by smallest member count with a createdAt tiebreak. For an MDU with distinct resident and visitor groups on different rates, approval silently assigns the billing relationship.

8. `removeMembership` (`apps/api/src/repositories/driver-group-memberships.ts:118`) has no caller and writes no audit row, and `driver_group_memberships` (`packages/shared/src/db/commercial.ts:356`) has only `added_at` — no status, no `removed_at`, no validity window. Both the Core revocation story and the per-month active-driver count need a column that does not exist today.
## C08 — Permissions, org scope, support context, audit

A real permission layer exists and is well tested at the unit level: a 26-verb per-tenant catalogue plus 16 platform verbs (`permissions.ts`), role bundles in code, a provenance-aware resolver (`resolvePermissionsWithProvenance`) that can tell "member of this org" from "Straumvakt staff", and a row-level `resolveOrgScope`. What is missing is the wiring: of 165 `requirePermission` call sites under `routes/` and `domains/`, only 32 pass `orgIdParam`, and only 8 of the 43 `billing.*` gates do — every rate, tariff and cost-factor write route takes the target org from the request body or query and gates on a bare `requirePermission("billing.write")`, which makes the org an unauthenticated input. Audit is a single writer function (`recordAuditAction` into `audit.actions`) called from 15 files, none of which is a rate, tariff, cost-factor or agreement route, and no route anywhere reads `audit.actions` back — the `audit.read` and `platform.audit.read` verbs guard zero endpoints.

**Area findings**

1. The bootstrap god-mode branch is effectively dead, which inverts a KNOWN FACT's practical consequence. `routes/admin/auth.ts:134-137` mints every cookie with `userId: resolvedUserId`, and Path A always resolves one via `bootstrapAdminUser`. `isBootstrapSession` (`require-permission.ts:216-220`) requires `userId === null`, so it returns false for every cookie issued in the last 12 hours. The live operator therefore takes the full DB path on the `super_user` PlatformGrant created at `repositories/admin-bootstrap.ts:84-95` — the early return only honours pre-Sprint-5.5 cookies, which have long expired. The branch still needs deleting, but Core must not assume it is what makes the console work.

2. Consequence of (1) plus the member-admin carve-out: driver and access-group management is 403 for the live operator right now. `super_user` holds every `platform.*` verb but `expandPlatformTenantVerbs` (`effective-permissions.ts:125-162`) filters `member.write/invite/remove` out via `MEMBER_ADMIN_VERBS`, and with no membership `viaMembership` is empty. Every route in GAP-06's list denies. The source comment at `domains/identity/routes/admin-users.ts:201-204` asserts "The bootstrap admin still passes, through the god-mode branch, so the operator console works today" — that comment is stale, and Core's manual-driver-management epic starts from a broken surface, not a working one.

3. An org-scoped pricing change is not provably org-scoped anywhere in the rate stack. `billing-tariff-mgmt.ts:42` takes `orgId` from the request body (`lib/billing/tariff-zod.ts:60`) behind `requirePermission("billing.write")` with no `orgIdParam`; `billing-rate-references.ts:97` does the same with `supplierOrgId` (`lib/billing/rate-reference-zod.ts:30`); `agreements-resolve.ts:27` resolves and persists billing lines for any session UUID. Because `resolvePermissionsWithProvenance` only queries `memberships` when `orgId` is non-null (`effective-permissions.ts:204`), passing no `orgIdParam` does not merely skip a check — it makes membership incapable of satisfying the verb at all.

4. Audit coverage of the Core-relevant surfaces is near zero. `recordAuditAction` is imported by 15 files; the only billing-adjacent ones are `bill-objects.ts` (`:107`, `:185`) and `driver-group-memberships.ts` (`:128`). No tariff publish, no tariff retire, no cost-factor create or deactivate, no rate-reference stage or retire, no agreement resolve writes a row. Separately, nothing reads `audit.actions` back — `audit.read` and `platform.audit.read` guard zero routes, confirming and extending the KNOWN FACT about `contract.write`/`tariff.write`: `tariff.read` and `billing.export` are dead verbs too.

5. `resolveOrgScope` (`org-scope.ts:38-76`) is the row gate and it is applied to 13 route handlers, all of them infrastructure reads (`sites.ts`, `chargers.ts`, `circuits.ts`, `installations.ts`, `properties.ts`, `active-sessions.ts`) plus exactly one billing route, `GET /api/admin/billing/tariffs` (`billing.ts:180-186`). `GET /api/admin/billing/sessions` instead builds its filter from `scopeFromQuery` (`billing.ts:57-67`), which reads `?orgId` straight off the query string with no validation — so the endpoint that backs CDR-derived driver statements has a caller-supplied tenant filter. `billing-summary.ts:36` returns a cross-tenant revenue leaderboard behind the same bare `billing.read`.

6. `permissionBasis` is computed on every non-bootstrap request (`require-permission.ts:88-92` and `:196-200`) and consumed by exactly one function, `redactForPlatformReader` (`admin-users.ts:138-154`). That is a ready-made, already-tested provenance signal that Core can stamp onto audit rows for free — `audit.actions` (`packages/shared/src/db/platform.ts:91-108`) has `metadata jsonb` and no dedicated column, so this needs a convention or a migration, but not new plumbing.

7. `SessionPayload` (`admin-session.ts:10-21`) already declares `userId?: string`, so the defensive cast and the "today's narrow SessionPayload type" comment at `require-permission.ts:230-233` are stale. More importantly the payload carries no acting-org and no support-context id, so every tenant decision has to come from the URL or a DB round trip — there is no cookie-side place to put "I am acting on org X for reason Y" without a schema change.
