Design rationale

  • Context chip silently updates from BLE → GPS → recent → most-frequent. Habitual users never tap it. The chevron and "From your last visit" / "Closest to you" subtext tell them why this location was chosen, so they trust it.
  • Bottom sheet groups by relevance, not alphabet. Right-here (BLE) → closest (GPS) → recent (behavioural) → all (escape hatch). Search at the foot for when access list grows past ~10 locations.
  • Single-install drivers see no chip. The current home screen renders unchanged; complexity scales with access scope.
  • BLE remains the hero. When a charger is in BLE range, the existing NearbyCard renders above the chip with one-tap start — the picker is only relevant when BLE doesn't fire.
  • No "default location" setting. Defaults are derived from signals, not a user preference toggle. Reduces config burden; matches Apple Maps' Home/Work pattern.
  • Backend cost: one new endpoint GET /api/driver/locations returning [{ installationId, displayName, lat, lon, freeCount, totalCount, lastUsedAt }] — plus the existing /api/driver/chargers already carries enough to derive these client-side, so the endpoint is an optimisation, not a requirement.
