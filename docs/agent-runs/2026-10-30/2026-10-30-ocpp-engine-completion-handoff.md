## 1. Mounted and wired source path

**Decision (from current source/config): host the engine as a NAMED `WorkerEntrypoint` (`EngineEntrypoint`) on the existing shell Worker `straumvakt-cpo-shell`, called by the gateway over a service binding with RPC.**

The shell already owns Drizzle and the `DATABASE_URL` requirement, so no new Worker.

## 3. Costing handoff (S1 explainable test costs)

- **No new money engine.** `src/lib/costing/cost-session.ts` calls the retained pure resolver (`@straumvakt/commercial` `resolveBillingLines` / `resolveFactor`) unchanged. The resolver returns an **empty list for a rate-less factor** — indistinguishable from a free session — so the consumer detects that case itself and names it.
- **Identity:** one authoritative session identity = `charging.ocpp_transactions.id`, written to `agreements.billing_lines.session_id` (`billable_event_type = 'session'`). Sealed original org/installation/placement/driver come from the transaction row (`placement` → circuit/site); agreements and rates are looked up on the SEALED installation/org at the **server** receive time of the start, never the charger's clock or the device's current owner. The legacy station/EVSE chain is not consulted. `loadAgreementContext` was ported to Drizzle (`drizzle-costing-store.ts`: installation agreement newest-wins with id tiebreak, workplace agreements for the org, membership by period, clauses/rules/rate refs).
- **Durability/idempotency:** one row per DB transaction: claim (`FOR UPDATE SKIP LOCKED`) → facts → decide → write lines + mark outcome, committed together. Outcome is exactly *costed with lines* or an explicit state: `unresolved_access` (no driver / no installation agreement / no membership), `unresolved_rates` (no clauses / a factor with no rate in force / resolver produced nothing), `unresolved_context` (placement missing, duration unusable, or a poison row parked after 5 attempts), `blocked_energy` (missing/bad energy), `excluded_unauthorized`. **Unknown is never zero**; unauthorized energy is never ordinary billable use. Re-running, concurrent runs and an interrupted write cannot double or lose lines (tests with a row-lock model). The physical transaction is complete and committed before costing runs; a costing failure cannot undo it.
- **Invocation, no cron:** after a StopTransaction result, best-effort via `ctx.waitUntil(runCosting(env, 3))`; and a deliberate bounded `EngineEntrypoint.costPending({limit ≤ 50})`. Re-queueing an `unresolved_*` row after fixing a rate/membership is an explicit operator action (set back to `needed`); no tooling for that exists yet (§9).
- **Schema:** migration `0005_ocpp_costing_handoff` (additive): `costed_at`, `costing_detail`, `costing_attempts`, partial index on `needed`, widened CHECK vocabulary (replaces 0003's check; a test requires the SQL list to equal the TypeScript union). No existing table's data is touched. **No uniqueness was added to `agreements.billing_lines`** (historical rows unknown → could break the build); idempotency is by the row-locked state guard plus a lines-exist check.
- **Not decided here (needs the accepted commercial contract):** sponsorship/workplace-payer semantics are carried over faithfully from the legacy loader, not extended; whether a rate in force should be judged at start or per-window (`start_rate` policy as the retained resolver does).
- Tests (VERIFIED, doubles): `costing.test.ts` (14): costed explainable lines; unauthorized; bad energy; missing rate (also a future-dated rate); each access gap; duration source; pricing by sealed context and server clock (a charger timestamp from 2001 cannot select an old rate); concurrent/duplicate runs; interrupted write; poison row; later rate fix; device moved CPO; outage while claiming.

## 5. Workload on an explicit timeline (assumptions stated; no prices applied)
One charger, one 2 h session 10:00–12:00, Heartbeat 3600 s, MeterValue interval 300 s, ~6 status changes, a visible chargers page open 10 min/day.
- **Correction of the earlier estimate:** the 60 s window could not coalesce 300 s readings. Now meter frames are due at the **next 15-minute wall-clock window boundary + a per-device offset (<60 s)**, so readings minutes apart share one flush per window; status frames flush in 5 s. Meter evidence is durable in the DO outbox until acked; billing does not wait on it (start/stop registers are committed synchronously).
- Per session, inbound WebSocket messages ≈ 2 (boot/heartbeats over the day separately) + 1 Authorize + 1 Start + 24 meter + 6 status + 1 Stop ≈ 33 (+24 heartbeats/day). Engine RPC calls: 1 admit/connection, Authorize 1, Start 1, Stop 1, status 6, **meter 24 (one RPC per frame — NOT batched into one call; a batch RPC would cut this to ≤ 9 and is an unbuilt improvement)**. Database transactions: Authorize/Start/Stop/status ≈ 9 + meter 24 + admit 1 + costing ≈ 1–3 → **≈ 35–40 DB transactions/session**. Meter **flush wake-ups ≤ 9 per session** (two hours / 15 min windows). DO storage: heartbeat/frames 2 ops each (liveness) + owner read once per wake + outbox ≈ 3 writes + 1 delete per meter frame.
- **Database requests ≠ compute wakes.** A request every few minutes may keep a compute active if the autosuspend interval is longer than the gap (the platform default is commonly 5 minutes; the project's actual setting is **NOT VERIFIED**). **No claim that Neon sleeps between bursts is made.** With 300 s meter gaps flushed every 15 min the long gaps are real, but overlapping chargers or visible UI polling (at most one DB-touching request per 120 s only when the hub is cold/aged out; otherwise none) can fill them. Failure retries add ≤ 12 attempts per entry with 5 s→15 min backoff.
- UI: hub-warm polls cost Workers + DO requests only; each change adds one device-state query. A cost figure and the proposed $30/month remain **unapproved**; no ceiling is promised. Computing it needs current prices and the verified suspend setting (Codex/Andri).
