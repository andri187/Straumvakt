## 1. Duplicate removal request (F2) — fixed
- The port signals `OpenRequestConflict` only for a `23505` on exactly `lifecycle_requests_one_open_per_device` or `lifecycle_requests_request_key_index`; **any other error or constraint propagates unchanged** (never turned into success).
- PostgreSQL aborts the failed transaction, so the service does NOT re-read inside it: it rolls back, then in a **new** transaction re-reads `byKey ?? openFor`, **re-authorises**, and returns the winner; if there is no winner it rethrows the original error.
- Resume rules (also on the non-race pre-check path): another organisation's request ⇒ the same `not_found` as none; same key for a **different device** ⇒ `conflict` (never the other request); an open request of a **different kind** ⇒ `conflict` (no silent reinterpretation); separate key + same device + same kind ⇒ the same request.
- Tests (VERIFIED, doubles): loser returns winner after rollback; foreign winner ⇒ `not_found`; unrelated constraint propagates; no-winner rethrows; same key/other device; separate keys; different kind; foreign key; 6 parallel requests ⇒ one request (serialised double). **Proves service logic only; the real `23505` handling needs the PostgreSQL run (T2/T5).**

## 2. Start vs removal vs closure — design and fix

**Analysis of the actual locking** (INFERRED from source and PostgreSQL's documented semantics; unexecuted):
- Isolation: `db.transaction` sets none ⇒ READ COMMITTED; each statement sees rows committed before it began.
- No foreign keys are declared in the Drizzle schema and none are created by migrations 0003–0007 ⇒ inserting an `ocpp_transactions` row takes **no** FK share locks on `placements`/`devices`/`installations`. (If the baseline migration 0000 created FKs, they would add `FOR KEY SHARE` locks that do not conflict with `FOR UPDATE` on a non-key update; to be confirmed in the PG run, T-L2.)
- Original start path: unlocked `startBlocked` read → insert; request: unlocked reads → insert; close: `installations FOR UPDATE` → count → update. The start never touched the installation lock ⇒ no mutual exclusion.

**Narrowest correct boundary: the PLACEMENT row, not the installation.**
- **start / Authorize** (`startGate`): `SELECT … FROM assets.placements WHERE id = ctx.placementId AND device_id = … AND upper_inf(period) FOR SHARE` **first**, inside the transaction that inserts the transaction. No row ⇒ the placement is closed ⇒ refuse (`placement_closed`). Then read open lifecycle requests (`blocked`) — a later statement, so it sees a request that committed while we waited.
- **removal request** (`lockPlacement`): `FOR UPDATE` on the placement **before** observing sessions.
- **close** (`closePlacement`): `installations FOR UPDATE` → `placements FOR UPDATE` → count open sessions → close or refuse (`SessionOpenError`).
- **Lock order everywhere: installation, then placement.** The start takes only the placement (never the installation), `applyStatus` takes only the installation, `installations` saves/moves take installation then update the placement ⇒ **no cycle** (model-checked over all 24 orderings of four writers, with and without a held first lock).
- **Both orders, outcomes:** start first ⇒ close/request WAIT, then see the committed session (close refuses; request includes it in its steps ⇒ the "cosmetic understatement" is closed too). Close/request first ⇒ the start WAITS, then sees the closed placement or the committed block ⇒ **refused, recorded as unauthorized evidence** (`placement_closed` / `service_blocked_removal`), never costed, never dropped. Retransmissions replay the stored answer without retaking the gate.
- Also fixed: `applyStatus` now ignores a status from a placement that is no longer open (a stale socket could otherwise write state onto a closed placement).
- **Stale admitted sockets:** the gate is the boundary (a refused start, an ignored status); stop/meter/late evidence are deliberately NOT gated so the session being ended can finish. The gateway still holds the socket until it disconnects; closing it proactively on identity close is not implemented.

**What is proven and what is not.** `src/lib/lifecycle/interleaving.test.ts` is an executable model of the lock protocol (FOR SHARE vs FOR UPDATE, READ COMMITTED visibility). It proves the PROTOCOL has no lost session and no deadlock for the scripted orders, and its **negative control** shows the original protocol loses the session. It does **not** prove PostgreSQL behaves as modelled or that the Drizzle queries take those locks (`.for("share")`/`.for("update")` generate the expected SQL — INFERRED, to be read back in the run).

### PostgreSQL concurrency spec (deterministic, two connections) — NOT RUN; needs approval for the exact target
Use two sessions A and B on one disposable-or-approved schema state with a seeded installation/placement/device (created through application code paths or reviewed SQL, never fabricated customer data). Control ordering with explicit `BEGIN`/`COMMIT` and a barrier (`pg_advisory_lock(k)` held by a third session, or sequential psql scripts); never `pg_sleep`-based timing.
- **L1 start-first:** A `BEGIN; SELECT … FROM placements WHERE id=:p FOR SHARE;` (hold). B `BEGIN; SELECT … FOR UPDATE;` → must BLOCK (check `pg_locks`/`pg_stat_activity wait_event='transactionid'|'tuple'`). A inserts a transaction row, `COMMIT`. B returns, `SELECT count(*) …open…` must be **1**; B refuses to close. Assert placement still open.
- **L2 close-first:** B `FOR UPDATE` + closes the period, holds. A `FOR SHARE` must BLOCK; B `COMMIT`; A's `upper_inf(period)` predicate returns no row ⇒ app refuses; assert one `unauthorized` transaction row and a `Blocked` receipt.
- **L3 request-vs-start both orders** with `lifecycle_requests` insert, asserting the start sees `blocked=true` (request first) or the request observes the session (start first).
- **L4 deadlock:** run closer (installation→placement), starter (placement), status writer (installation) in all orders, 200 iterations each with random barriers; assert zero `40P01`.
- **L5 close vs late start (stale socket):** after L2, replay the start: still refused; replay a `StopTransaction` for an earlier session: accepted.
- **T2/T5:** two parallel `INSERT`s into `lifecycle_requests` for one device ⇒ exactly one `23505` naming `lifecycle_requests_one_open_per_device`; `requestKey` duplicate ⇒ `…request_key_index`; a different unique violation ⇒ unmapped.
- **L6 isolation assumption:** `SHOW default_transaction_isolation` on the approved target = `read committed`; if it is `repeatable read`, `FOR SHARE/UPDATE` on a row changed after the snapshot raises `40001` and the app must retry (not handled today) — **record the observed value before relying on any of this**.
- **Expected failure modes to look for:** `40P01` (deadlock), `40001` (serialization), a close that commits with an authorized open session (must be impossible), an authorized transaction with a `placement_id` whose period closed before `started_received_at` (must be impossible).

## 3. Superseded and missing-stop sessions (F1) — fixed without fabricating evidence
- The engine's `reconcile_flag = 'superseded_by_new_start'` is now a shared constant (`SUPERSEDED_FLAG`). The lifecycle treats such an **open** row as **non-gating but UNCONFIRMED**: no stop command is sent for an id the charger abandoned, `closePlacement`/`openSessionCount`/the plain-save guard exclude it, `stopConfirmedAt` stays null, **no stop is invented, the engine's evidence is untouched, no cost is run**, and the step shows `settlement: held (stop_unconfirmed_superseded)`.
- If the charger's real `StopTransaction` for that id ever arrives, the engine applies it normally (late evidence preserved) and the transaction is queued for costing; the **completed request is a terminal snapshot and does not rewrite itself** (the operator sees the live settlement on the session record). Limitation recorded.
- A genuinely open **superseding** session still gates removal and needs a real stop.
- **Physical-confirmation limit (stated, not hidden):** a new `StartTransaction` on the connector means the charger itself moved on, which under OCPP implies the earlier transaction ended; it is **not** evidence of when, or of how much energy. Pricing needs a charger stop or operator evidence.
- **Auditable reconciliation route — DESIGN (not built):** an operator action `reconcileSession{transactionId, reason, evidence: {stoppedAt, meterStopWh?, source}}`, shared-login attributed, recorded in a new append-only `charging.ocpp_transaction_reconciliations` (actor, reason, evidence JSON, previous state, time) and applied by the **engine's own stop path** with provenance `operator_reconciled` (so `computeEnergy` quality rules still apply and a missing/contradictory meter stays `blocked_energy`, never zero). It never edits `stopped_*` silently, never settles automatically, and a later real `StopTransaction` is flagged `conflicting_stop` against it. Needs a product decision on who may reconcile and the evidence standard (§8).

## 4. Immutable historical terms and payer — implemented
- **Contract:** at `StartTransaction` (accepted driver only) the engine reads the applicable terms **once**, as of the server start time (installation agreement newest-wins with id tiebreak, workplace agreements for the org, membership by period, clauses by period, bearer rules, rate references) and stores them on `charging.ocpp_transactions.terms_snapshot`: JSON with schema version, evaluation time, capture time, the facts (bigint/date-safe) and a **sha-256 over canonical JSON**. Refused/unauthorized/removal-blocked starts carry no snapshot (never costed).
- **Enforcement:** migration **0007** adds the column and a `BEFORE UPDATE` trigger `ocpp_transactions_terms_immutable` that raises `23514` if a non-null snapshot would change (a NULL snapshot may be set once). Additive; nothing read or written by the migration. **UNVERIFIED in PostgreSQL.**
- **Costing reads ONLY the snapshot.** It revives and **verifies the hash**; a missing snapshot (started before this contract), `status: missing` (capture failed / not available), an unknown schema or a tampered hash is `unresolved_context` with a named reason (`terms_not_captured`, `terms_snapshot_tampered`, `terms_snapshot_unknown_schema`). **The mutable term tables are never a fallback.** Each costed result records `termsSha256` and `termsAt` in `costing_detail`, so the derivation is answerable and tamper-evident.
- **Capture failure never blocks charging** (S1 pre-commercial): the start is accepted and the snapshot honestly says `capture_failed`; the session is costed as an explicit unresolved state. (Decision to confirm in §8.)
- **Sponsorship:** evaluated wholly at start, which is the adopted cutoff rule (an ongoing session keeps its coverage through completion, including energy after revocation); no mid-session re-evaluation was added, so nothing contradicts the adopted decision. Partial-factor coverage is whatever the clauses/rules in the snapshot say.
- **Tests (VERIFIED, doubles):** an in-place rate edit between start and first costing cannot change price/payer; a backdated newer rate row cannot re-price; an edit after costing changes nothing and the detail names the snapshot hash; bigint/date round-trip; tampered/unknown/legacy/failed-capture snapshots are never priced; sponsorship at start preserved; the hash is a function of the terms only; the engine captures once, not on replays, not for refused starts, and records `capture_failed` / `capture_not_available`.
- **What remains:** the mutable term tables are still editable (the snapshot protects started sessions, not the tables); making them append-only is a separate guarantee (B1a). Whether a rate correction after a session should re-price it remains a **product decision** (today: no — an explicit operator re-queue with a freshly captured snapshot is the only route, and no UI/tool exists for it). `ended_at` for the resolver is still synthesised from the start plus the measured duration; harmless while selection is wholly at start (pinned in the code comment).

## 5. Closed-identity attempts (F5) — logged
Admission now records a connection attempt from a KNOWN identity whose period or placement has ended (`identity_not_current`, `no_active_placement`) via the existing throttled `pending_discoveries` upsert, with the reason in `last_payload_summary`. It never grants anything; the refusal and its wire status are unchanged; a write failure cannot change the refusal. This gives an operator the "retired device reconnecting" signal the retirement policy asks for, without an operator UI (none built). Evidence for a **late `StopTransaction`/`MeterValues`/contradictory stop after the close is still impossible to receive** (admission refuses the connection): bounded recovery path is not built; mitigated because closure requires every gating session's durable stop first. Superseded sessions are the known exception (§3).
