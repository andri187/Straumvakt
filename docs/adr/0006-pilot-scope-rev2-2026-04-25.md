# ADR 0006 — Pilot Scope Rev 2 (2026-04-25)

> **LEGACY — pre-market-focus historical reference. Not active canon. See /FOCUS.md. Load-bearing constraints extracted into the focus rules.**

**Status:** Accepted
**Date:** 2026-04-25
**Supersedes (in part):** ADR 0005 — does not revoke ADR 0005, extends it.
**Sprints affected:** structure changes — pilot adds Sprints 2 and 4, removes
Sprint 4 (Driver Experience) and Sprint 6 (Issue Engine) entirely.
**Rollback anchors:**
- `pilot-rescope-rev1-2026-04-25` — state after ADR 0005, before this ADR
- `pre-pilot-rescope-2026-04-25` — state before any rescoping

## Context

ADR 0005 tightened pilot scope by deferring six topical groups (A–F)
to post-pilot. After reviewing the visual roadmap, the operator made
four further structural calls:

1. The pilot needs **admin onboarding tooling** — admin-side CRUD for
   the entire entity hierarchy (Org → Host → Property → Site →
   Installation → Circuit → Charger → OCPPIdentity → Connector) plus
   member invites — landing **early**, before everything downstream
   tries to test against real-shaped data.
2. **Zaptec API enrichment** is part of charger onboarding, not a
   separate later track. The Zaptec OAuth flow + API enrichment
   should ride alongside the admin charger onboarding wizard.
3. **Charge log retention machinery** (the V3 §8 retention classes)
   needs explicit sprint scope — nightly aggregation, raw_protocol
   ageing-out, cold-archive scaffolding. It was implicit in Sprint 1
   but never milestoned.
4. **Pilot is admin-functionality only.** No driver-facing surface
   during pilot. Drivers exist as admin-created records; no PWA
   self-signup, no driver login, no QR start, no family group UX —
   the entire Sprint 4 Driver Experience moves to post-pilot.
5. **Issue Engine moves entirely to post-pilot** (not just the
   advanced features ADR 0005 deferred — the basic five rules and
   ticket workflow too). Pilot operator diagnoses by hand from the
   raw event log.

Schema for all of this exists already, with one exception: **Circuit**
was deliberately flattened out of V3 in the original architecture
(CPMS had Site → Installation → Circuit → Charger; V3 had Site →
[Installation] → SiteAsset). Re-adding Circuit is documented
separately in ADR 0007.

## Decision

### Sprint structure

Two new sprints inserted, two existing sprints removed. Net: pilot
length grows by one sprint (was 11, now 12 if you count Sprint -1).

**Pilot sprints — the new sequence:**

| New # | Sprint | Status | Notes |
|---|---|---|---|
| -1 | Login Shell | DONE | unchanged |
| 0 | Foundation Schema | DONE | unchanged |
| 1 | OCPP Foundation | DONE 1.5 | unchanged |
| **2** | **Admin Onboarding + Zaptec API Enrichment** | NEXT | **NEW.** Org/Host/Property/Site/Installation/Circuit/Charger/OCPPIdentity admin CRUD; member invites; charger onboarding wizard with Zaptec OAuth + API enrichment; beta operator console shell; billing UI scaffold. |
| 3 | OCPI Foundation (CPO-only) | FUTURE | was Sprint 2 |
| **4** | **Data Storage Lifecycle** | FUTURE | **NEW.** Nightly aggregation of raw_protocol → aggregate; raw_protocol ageing-out at 30–90 days; financial + operational kept hot indefinitely; cold-archive scaffolding for issue_history; first concrete implementation of V3 §8 retention classes. |
| 5 | Commercial Model (ISK only) | FUTURE | was Sprint 4 |
| 6 | Billing Dashboard | FUTURE | was Sprint 6. **Issue Engine slot removed entirely** — see post-pilot below. |
| 7 | Push API + Observability | FUTURE | was Sprint 7 |
| 8 | Hardening | FUTURE | was Sprint 8 |
| 9 | Multi-Tenant + White-Label | FUTURE | was Sprint 9 |
| 10 | Pilot Go-Live (admin-only) | TARGET | was Sprint 10. Reframed: no driver onboarding during pilot. |

**Removed from pilot entirely (now post-pilot):**

- Old Sprint 3 — Driver Experience
- Old Sprint 5 — Issue Engine + Operator Console (the operator console
  *shell* moves to new Sprint 2; Issue Engine + helper role + ticket
  workflow + advanced detection all defer)

### Post-pilot backlog updates (extends ADR 0005 tags A–F)

Tags A, C, E, F unchanged. **B and D expanded.**

- **B · Driver Experience** — was just Auðkenni + QR. Now: entire
  Driver Experience sprint deferred. Driver self-signup, login (any
  kind), driver PWA shell, Auðkenni eID, QR-code session start,
  family groups, employer reimbursement workflow. Pilot drivers
  exist as admin-created records only.
- **D · Issue Engine** — was just v2 advanced. Now: entire Issue
  Engine sprint deferred. Five basic detection rules, ticket
  workflow, helper role, charger lifetime history, operator
  console *issue pages* — all post-pilot. The console *shell*
  (sidebar, topbar, role-based nav, placeholder pages) ships in new
  Sprint 2; the issue-specific pages are what defer.

### Admin-side Driver creation (new clarification, in pilot)

Drivers exist in the V3 schema (`identity.users` + `tenancy.memberships`
with `role=driver`). Sprint 2 milestone 2.2 (admin user/membership
CRUD) covers admin-side driver creation: an admin operator creates
a driver record, assigns them to an Org, optionally links an RFID
card. **What they cannot do in pilot:** sign in to anything (no
driver-facing surface), receive an invite email (no email pipe),
or self-onboard. They are inert records linked to OCPP idTags so
the operator can see "this RFID at this charger maps to this person."

## Consequences

### Positive

- **Admin tooling lands early.** Sprint 2 unblocks every downstream
  sprint — OCPI Foundation (Sprint 3) tests against real Sites and
  Chargers; Commercial Model (Sprint 5) tests against real Plans
  attached to real Hosts; Billing Dashboard (Sprint 6) reads real
  session data tied to real Chargers.
- **Zaptec is concrete from the start.** The vendor adapter track
  ships with a working Zaptec adapter as its first instance, not as
  an abstraction without an implementation.
- **Charge log retention is explicit.** Sprint 4's lifecycle work
  catches up with the V3 §8 architecture before pilot. Without it,
  raw_protocol events would accumulate indefinitely.
- **Pilot is honest.** Calling pilot "admin-only" stops the operator
  pretending the platform has features it doesn't. Drivers and Issue
  Engine come post-pilot, with proper attention.

### Negative

- **No driver-facing surface during pilot.** Pilot drivers can't see
  their own session history, family group, or any Straumvakt-branded
  UX. They use chargers like a generic OCPP installation; only the
  operator has visibility.
- **No Issue Engine during pilot.** When a charger goes wonky, the
  operator queries `events.event_log` directly and reads the raw
  state. Manageable at single-pilot-site scale (≤10 chargers); not
  manageable at production scale.
- **Pilot is one sprint longer** than the rev-1 plan (was 11, now
  12 counting Sprint -1). Two added (Admin Onboarding, Data
  Lifecycle) minus two removed (Driver Experience, Issue Engine
  basic) plus the original +1 from rev 1's not-yet-applied insert
  = net +1.
- **Circuit returns to the schema** (per [ADR 0007](./0007-circuit-asset-tier-back.md))
  — additive but a real schema migration. Sprint 0's foundation
  schema is no longer the final word; Sprint 2 milestone 2.6 ships
  the Circuit migration.

### Neutral

- ADR 0005 tags A, C, E, F unchanged.
- Schema for everything in Sprint 2 already exists from Sprint 0
  except Circuit (ADR 0007).
- The admin console shell built in Sprint 2 is the same shell Sprint
  9's multi-tenant work re-skins — no rebuild.
- Pilot Go-Live (Sprint 10) is now framed as "admin-only,
  demonstrable platform" — the framing matches the underlying truth.

## Alternatives considered

**Keep Driver Experience in pilot, ship a minimal PWA.** Rejected —
"minimal" tends to grow under pilot pressure; the Auðkenni paperwork
alone is multi-week. Better to defer the entire surface than ship
a broken half.

**Keep basic Issue Engine in pilot, defer only advanced.** Rejected
— even basic Issue Engine has a UI surface (ticket pages, helper
role, lifetime history). Operator can run pilot with hand-queries
against the event log; that's sufficient for site-scale operation.

**Don't add Data Storage Lifecycle as its own sprint; embed in
Sprint 1.6.** Rejected — Sprint 1 is closed at 1.5; reopening it
breaks Rule 11 (sprint discipline). New milestone in a fresh
sprint is the correct shape.

**Bundle Zaptec into Sprint 3 OCPI alongside roaming.** Rejected —
Zaptec API is a vendor adapter, not OCPI. They share neither code
nor concepts. Bundling muddles both.
